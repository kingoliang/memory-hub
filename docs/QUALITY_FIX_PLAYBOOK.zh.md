# 代码质量修复操作规程

来源：2026-09-03 对 loganalysis 的确定性工具审计与实修（lizard / node --test coverage /
Stryker / knip / madge）。所有条目附实测数据，不是理论建议。

> **给正在重构复杂度巨兽的人：先读第 5 节陷阱一。** 降 CCN 是本规程明确
> **不推荐**的整改目标，而且门禁绝不能设 CCN 上限。

---

## 0. 前置：先建立可信基线，再动任何代码

修之前必须有**真实数字**，否则你在优化幻觉。

```bash
lizard <src> --exclude "*/node_modules/*" --exclude "*/vendor/*" -C 10   # 复杂度
<test-runner> --coverage                                                 # 覆盖率
stryker run / mutmut run                                                 # 变异测试
knip / vulture                                                           # 死代码(高误报)
madge --circular                                                         # 依赖环
```

**覆盖率必须自己重算分母。** 多数工具只统计"被加载过"的文件；没有任何测试 import 的模块
**不显示 0%，而是根本不出现**。loganalysis 因此读作 72.06%，真实值 **35.4%**
（38 个源文件里 18 个完全缺席）。

```
真实覆盖率 = Σ(每文件行数 × 该文件覆盖率) / Σ(全部源文件行数)
分母来自 git ls-files，不是工具输出
```

## 1. 优先级排序：按风险 × 可行性，不按指标数值

**CRAP 最高的那个通常不该第一个动。**

| 序 | 类别 | 判据 |
|---|---|---|
| 1 | **安全/权限代码无断言** | 变异体存活即等于无保护。工作量小、风险为零、收益最高 |
| 2 | **已证实的死代码** | 必须先过第 4 节核实程序，否则会删掉活代码 |
| 3 | **高变更频率 × 零覆盖** | `git log --since='90 days' -- <file> \| wc -l` 与复杂度交叉 |
| 4 | **新写的容错/修复代码无回归测试** | 它修的 bug 会静默重现 |
| 5 | **高覆盖低变异得分** | 测试在调用而没在检查 |
| 6 | 清理构建产物 | 零风险，随手做 |

**不要**把 CRAP 排名直接当修理顺序。loganalysis 里 CRAP 第一名（870）排到第 3 位，
因为它是高频变更的核心链路，正确动作是补测试而非重构。

## 2. 各类问题的标准修法

### 2.1 无测试保护（变异体存活）

**把存活变异体当规格说明，而不是猜该测什么。** 但**按契约写断言，不要逐个追变异体** ——
追变异体会写出一堆脆弱的镜像测试。

关键手法：**断言完整集合而非若干项** —— 但期望值必须是**写死的字面量**。

```js
// ✗ 删掉任意一条都不会失败
for (const t of ['Write','Edit']) assert.ok(LIST.includes(t));

// ✗✗ 更隐蔽:期望值从被测模块推导 = 镜像测试
//    变异体改了源码,EXPECTED 跟着变,断言恒真,变异体必然存活
const EXPECTED = Object.keys(CONFIG).filter(k => CONFIG[k].enabled);
assert.deepEqual(actual, EXPECTED);

// ✓ 期望值写死,与源码解耦
assert.deepEqual([...LIST].sort(),
  ['Write','Edit','MultiEdit',/* …逐条列全… */].sort());
```

实测：`agent-hardening.js` **50.68% → 94.52%**（字面量写法）；
mr-quality-gate 某模块用推导式期望值卡在 **63%**，改成字面量后 **91%**。

正则要逐分支给用例；可选量词（`\s*`）零匹配和多匹配都要测；optional chaining
传畸形输入断言**不抛异常**。

### 2.2 复杂度巨兽

**先补测试钉住行为，不要重构。** 且**不要**把降 CCN 当目标（见陷阱一）。
CCN 只作为"哪里需要测试"的指示器，不作为门禁。

### 2.3 死代码

**默认假设工具是错的**（见第 4 节，这是踩得最惨的一处）。

确认是死代码后：能删则删；若只是"未被外部 import 但内部在用"，正确动作是
**去掉 `export` 关键字**，不是删函数。

### 2.4 覆盖率幻觉

不要修数字，要修**分母口径**：门禁按版本控制的文件清单重算，未加载文件按 0% 计入。

## 3. 验证闭环：三步，缺一不可

```
测量 → 修改 → 复测同一指标 → 贴出前后数字
```

1. 改前记录基线数字（不是"感觉不够"）
2. 改后跑完整回归：全部测试 + **真实 import 每个生产模块**（语法检查不够）+ 关键端点冒烟
3. 用同一工具复测同一指标，前后并列

**测试通过不算验收，覆盖率也不算。** 只有变异得分回升才证明断言真的在看着代码。

**行为等价性证明**（声称"无行为变化"时必做）：

```bash
git show HEAD:./path/file.js > /tmp/old.js
# 对同一组输入，逐一比对新旧版本输出
```

**等价变异体要识别出来并停手。** loganalysis 剩余 4 个存活全是等价变异体，其中 2 个还顺带
证明了某条正则分支是冗余的（任何 `>>` 都已被 `>` 分支匹配）。追它们是浪费。

## 4. 实修踩过的坑

### 坑一：用工具的方法验证工具，等于没验证 ⚠️ 最严重

审计报告了"3 个死导出 + 2 个孤儿文件"，**全错**。照做会破坏 `evals/self-evolve.mjs`。

knip 在子目录下运行，看不到：兄弟目录**反向 import**、HTML 的 `<script src>`、
二进制 spawn（`node_modules/.bin/*`）。

**而核查用的 grep 重复了同一个边界** —— 只搜当前包、还排除了定义文件本身（掩盖内部调用）。
两个独立来源给出一致的错误答案，看起来像相互印证。

最终结果：**14 个"未使用导出"，零个是死代码。**

删代码前的强制程序，三项全空才可删：

```bash
grep -rn '\bSYM\b' <整个仓库,不只当前包> | grep -v node_modules   # 含定义文件
grep -rn 'SYM' *.html                                             # HTML 引用
grep -rn 'SYM\|<bin-name>' --include='*.json' .                   # 二进制/脚本调用
```

### 坑二：把 "unused export" 读成 "dead code"

工具说的是"没有外部按名 import"，不是"零引用"。两回事。

### 坑三：空覆盖率报告显示 100%

命令写成 `node --test test/` 时 Node 当模块路径解析失败，**却仍输出
`all files | 100.00%` 的空表**。看到 100% 先确认表里有没有文件行。

### 坑四：变异测试耗时估算差 5 倍

按初始试跑速度（1.7s）估 2084 个变异体 = 15 分钟，实际单体约 8 秒，36 分钟没跑完被超时杀掉，
**Stryker 只在结束时写报告，被杀即一无所得**。

**分批串行跑**，每批控制在 10 分钟内。并行反而更慢（抢 CPU，试跑从 1.7s 涨到 7.9s）。

### 坑五：`npm install` 会修剪 node_modules

装审计工具时提示 "removed 112 packages"。即使 `--no-save`，也**必须事后逐一验证生产依赖仍在**，
包括 `.bin/` 下的二进制。

### 坑六：重启会暴露"内存里活着"的故障

改完重启后 Teams 轮询全瘫：依赖的 MCP server 升级后改用加密缓存格式，读取方只认旧格式。
旧进程内存里有有效 token 所以一直没暴露。**症状极具误导性** —— 刚成功登录，报错却和
"从没登录过"一模一样。

教训：**验证必须覆盖重启后的冷启动路径**，不能只看进程还活着。跨组件格式升级，
先找同仓库有没有已处理过的实现可移植。

### 坑七：期望值从被测模块推导 = 镜像测试 ⚠️

"断言完整集合"只有在**期望值写死**时才成立。任何 `import` 被测模块再加工得到的期望集合，
都会随变异体一起变化，断言恒真：

```python
# ✗ 镜像测试:改 SOURCE 里的任何一项,EXPECTED 同步变,测试永远绿
EXPECTED = {k for k, v in module.SOURCE.items() if v.enabled}
assert actual == EXPECTED
```

实测卡在 63%，把 EXPECTED 换成字面量后升到 91%。**期望值必须能被人读懂、能被 code review
逐条核对** —— 如果它是算出来的，它就不是期望值，是复述。

### 坑八：子串断言对"包裹型"变异体天然免疫

变异操作符不同，断言强度要求也不同：

| 工具 | 字符串变异 | `assertIn` / `assert.match` 是否有效 |
|---|---|---|
| mutmut (Python) | `"foo"` → `"XXfooXX"` | **无效** —— 原串是变异串的子串，恒真 |
| Stryker (JS/TS) | `"foo"` → `""` 或 `"Stryker was here!"` | 侥幸有效 —— 变异串不含原串 |

→ **一律用整值断言**（`assertEqual` 整行 / `assert.deepEqual`），不要依赖工具恰好用了
哪种操作符。Python 侧尤其致命：`assertIn("expected text", output)` 是最常见的写法，
而它对 mutmut 完全免疫。

实测（mr-quality-gate，改整值断言后）：`live_config` **35% → 93%**，
`jira_context` **23% → 91%**。

### 坑九：不要删未提交改动的备份

`.bak` 是未提交生产改动的唯一回滚手段。**先提交，再清理。**

## 5. 三个必须写进规程的度量陷阱

### 陷阱一：度量奖励删守卫代码 ← 重构复杂度巨兽前必读

每个 `if`/`catch` 都是一条分支。某函数 CCN 29 里 **18 个来自 catch 块**，全删掉
CCN → 11、CRAP 870 → 121 —— **指标大幅改善，代码更脆弱**。那些 catch 是为了让一次 API 抖动
不至于丢掉跑了 10 分钟的分析。

→ **门禁绝不能设 CCN 上限。** 只报告，不作为失败条件，理由写进脚本文件头。

→ 重构巨兽时的正确判据不是"CCN 降了多少"，而是**行为等价性 + 变异得分不降**。
拆函数若把 catch 合并或吞掉，即使 CCN 大降也是退步。

### 陷阱二：变异得分的分母由作者控制

删掉功能连同它的测试，得分反而上升。实测：删掉 3 个死导出，变异得分
**31.51% → 52.46%（+20.9 点，一行测试没加）**。

那次恰好该删，但同样操作用在活代码上就是造假，**数字上完全无法区分**。
→ 删代码前必须走第 4 节核实程序。

覆盖率 72% vs 35.4% 是同一机制的被动版本：没人作弊，分母自己缩水了。

### 陷阱三：CRAP < T 实质是 CCN 硬上限

`CRAP = CCN²×(1−cov)³ + CCN`。覆盖率 100% 时 `(1−cov)³ = 0`，**CRAP 退化成 CCN 本身**。

所以 "CRAP ≤ 8" 在充分测试的代码上就是 **"CCN ≤ 8"** —— 与测试质量无关的结构上限。
这条门禁强制的是**拆函数**，不是"写测试"。当质量指标用，会得到一堆为过闸而机械切碎、
参数列表冗长的小函数。

## 6. 收尾：把规程变成流水线里的失败条件

**审计只有变成 CI 的退出码才有意义。** 三层：

1. **门禁脚本** —— 阈值破线退出码非零
   - 覆盖率**按版本控制的文件清单重算分母**
   - 变异得分读工具产物（全量太慢，CI 定时跑，门禁读产物）
   - **复杂度只报告，永不失败**，理由写在文件头
2. **包管理脚本** —— `gate` / `mutate` / `complexity` / `deadcode` / `cycles`
3. **项目根 `CLAUDE.md`** —— 每个 agent 会话开局自动加载，含三条禁令：
   - 不许为降 CCN 删守卫代码
   - 不许靠删代码提升变异得分（删前必须走核实程序）
   - **不许下调阈值让构建变绿**

**阈值设为今日实测值下方，是棘轮不是理想值。** loganalysis 设的是覆盖 35.0 / 变异 34.0
（实测 35.4 / 34.88）—— 今天的代码能过，任何回退会失败。

## 7. 变异测试执行卫生（2026-09-28，一天内三次假结果换来的）

变异测试的结论只有在**执行过程本身可信**时才有意义。以下五条，每次都要做：

1. **绝不用 `pkill -f` / `pgrep -f` 匹配一个出现在自己命令行里的字符串。** 变异脚本、shell 的命令行里
   往往就含着那个标记——实测把自己的变异运行器杀了两次。按确切 PID 结束进程，或读 `/proc/<pid>/cmdline`
   精确匹配 `argv[1]`。
2. **每个变异体跑完都断言源文件已还原**（`assert open(F).read() == 原文`），整批前后再比一次 diff 行数。
   实测：一次被打断的运行把源文件留在变异状态，下一批在坏版本上报了三个毫无意义的 KILLED——是 diff
   行数对不上才发现的。
3. **每个判定跑两次，两次一致才算数。** 已有的不稳定测试（实例：logalert `proxy: SSE streams chunks
   without buffering`，≥10ms 计时断言，5 次里失败 1 次）会把存活的变异体伪装成"被杀"。必要时只跑与
   变异相关的测试子集，避开已知不稳定的测试。
4. **在副本 / git worktree 上跑，永远不在生产在用的目录树上跑**（节点 01 的 runner 直接用 live tree）。
5. **新代码上存活的变异体，可能说明这段改动本来就不需要。** 先问"去掉它行为变不变"，不变就撤回改动，
   而不是硬凑一个测试把它杀掉。（实例：ai-core MCP 泄漏修复里"把超时移进清理内层"的改动。）

## 8. Bob 看不到的三类问题

变异测试回答的只是"**已有的测试**能不能察觉代码被改动"。它**不能**回答"代码有没有 bug"。以下三类
在 2026-09-28 一起出现（常驻的 logalert 进程泄漏了 100 个 MCP 子进程，拖垮了门禁所在的机器）：

1. **没人写过测试的路径。** 变异只在被审计的代码上做；一条从未被测试触达的路径（超时 + 清理），
   变异得分再高也看不见它。**对策：** 审计时列出"错误路径 / 超时路径 / 清理路径"，逐条确认有测试。
2. **第三方库的行为。** 泄漏根源是 agno `MCPTools.__aexit__` 把异常传进了清理流程。变异只改我们的代码。
   **对策：** 用真实依赖（真实子进程、真实库）写集成测试，断言外部可观察的结果（进程数、文件、端口）。
3. **只在长时间运行里才出现的问题。** 每次超时漏一个进程，单次测试毫无迹象，常驻进程里跑 10 天漏到
   100 个。**对策：** 对常驻服务加"同一个事件循环 / 同一个进程里连续调用 N 次 → 资源回到基线"的测试；
   上线后盯进程数、子进程数、CPU、内存的趋势，而不是只看单次结果。

---

## 9. 一句话总结

> 让工具指出问题，但**换一种独立方法核实**；用变异得分而非覆盖率验收；
> **期望值写死、断言整值**；**指标能被删代码改善的那部分，永远不要设成门禁**。
